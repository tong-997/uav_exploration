# 实验 4B 与主探索系统的接口说明

> 生成时间：2026-06-06

## 1 为什么 Exp 4B 独立于 ExplorationSystem

### 1.1 系统架构差异

| 维度 | 主探索系统 (Exp 1–6) | 跟踪/围捕系统 (Exp 4B) |
|------|---------------------|----------------------|
| 核心任务 | 未知区域探索（前沿驱动） | 已知目标跟踪与围捕 |
| 栅格地图 | 必须：200×200 占据栅格，实时更新 | 不需要：目标位置已知 |
| 前沿检测 | 必须：驱动探索方向决策 | 不需要：无前沿概念 |
| Voronoi 分区 | 必须：区域分配 | 不需要：围捕槽位分配替代 |
| 路径规划 | A* on grid → waypoint following | 直接向目标/槽位移动 |
| 感知模式 | 深度传感器 → ray-cast → 栅格更新 | 目标检测 → KF 更新 |
| UAV 数量扩展 | 1/2/3（Exp 1 消融） | 3 固定（围捕需要 ≥3） |

### 1.2 关键区别

主探索系统的核心循环是：
```
感知 → 栅格更新 → 前沿检测 → Voronoi 分区 → 目标选择 → A* 规划 → 路径跟随
```

Exp 4B 的核心循环是：
```
目标运动 → 视觉检测 → KF 预测/更新 → 重关联 → 状态广播 → 融合 → 围捕槽位计算 → FSM 状态转移 → 移动
```

两个循环共享的底层组件仅有：
- `SimEnvironment`：提供障碍物和环境初始化
- `detect_target()`：视觉检测接口
- `AStarPlanner`（可选）：Exp 4 协同响应中使用

### 1.3 独立运行的好处

1. **测试隔离**：跟踪/融合/围捕的正确性不受建图误差干扰
2. **参数独立**：跟踪实验使用 500 步，围捕使用 600 步，与探索的 800 步无关
3. **可复现性**：无需等待探索到目标附近才触发跟踪，UAV 直接从目标近处开始
4. **组件验证**：每个子实验单独验证一个技术组件（KF → 融合 → 围捕），便于消融分析

## 4 与主系统的衔接点

### 4.1 数据流衔接

在完整的侦察-打击场景中，系统运行分两个阶段：

**阶段一（Exp 1–3, 6 对应）：** 探索阶段
- UAV 自主探索未知环境，构建栅格地图
- 前沿探索 + Voronoi 分区 + 分布式防撞

**阶段二（Exp 4, 4B 对应）：** 目标发现后
- 探索过程中通过视觉检测发现目标（Exp 4 验证的机制）
- 触发协同响应，切换到跟踪/围捕模式（Exp 4B 验证的机制）
- 此时不再需要前沿探索和栅格更新

### 4.2 触发条件

Exp 4 已验证的 3 帧确认机制是两个阶段的桥梁：
```
探索模式 → [目标检测 × 3 帧确认] → 跟踪/围捕模式
```

### 4.3 论文中的定位

Exp 4B 在论文中应定位为"目标发现后的下游处理能力验证"，与主探索系统形成前后衔接的完整闭环，而非在探索循环内部的嵌套功能。

## 5 为什么不做端到端集成测试

1. **探索阶段的不确定性**：目标发现时刻依赖随机种子和障碍物分布（Exp 4 中 step 207~243），发现后的可用步数不确定
2. **变量混杂**：端到端测试中，跟踪精度同时受建图质量、探索效率和检测模型影响，无法隔离 KF/融合/围捕的独立贡献
3. **已有充分的模块级验证**：
   - Exp 4：检测→确认→协同响应（探索→跟踪的切换）
   - Exp 4B-1：跟踪精度和连续性
   - Exp 4B-2：多机融合
   - Exp 4B-3：围捕编队
4. **论文工作量合理性**：2D 仿真系统的端到端集成测试的学术贡献有限，模块级验证已足够支撑论文结论
